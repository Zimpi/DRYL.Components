# I1 — AI parameter naming: Implementation Plan

**Datum:** 2026-08-11
**Quelle:** [`../ideas/I1 AI parameter naming for AI-native components.md`](../ideas/I1%20AI%20parameter%20naming%20for%20AI-native%20components.md) (State `Ready`, Direction C)
**Voraussetzung:** Phase B abgeschlossen (`86fbf25`), `I3` (`2ccc3d7`) und `I2` (`3a78b18`) umgesetzt.

**Ziel:** `AI-03` sagt heute unqualifiziert „der `AiState`-Parameter heißt `Ai`" und
zählt acht Verstöße. `I1` hat entschieden: die Regel gilt dem **Opt-in-Parameter**, der
Test ist `AiState.None`. Fünf der acht sind damit keine Verstöße, drei werden umbenannt.
Dieser Plan setzt beides um — den Regeltext und die drei Renames — und schreibt dabei
die ersten drei Component-Specs der Bibliothek.

## Warum überhaupt Specs in diesem Plan

`I1` fasst Komponentencode an, und `SPEC-01` verbietet Code für eine Komponente, deren
Spec man nicht gelesen hat. Unter `specs/E3 AI/` liegen bisher nur die beiden
Gerüst-Begleitdateien. `IDEA-07` setzt eine Idee außerdem erst auf `Adopted`, wenn sie
in Specs überführt ist — ohne Spec bliebe `I1` auf `Ready` stehen, obwohl der Code
schon umgebaut wäre.

Deshalb ist die Einheit eines Tasks hier **Spec + Code derselben Komponente in einem
Commit**. `SPEC-04` deckt genau diesen Fall ab: „Spec and code changed together in one
session: go straight to `Implemented`" — kein Umweg über `Modified`, und die Spec
beschreibt von Anfang an den Zielzustand, nicht den Ist-Zustand von vor dem Rename.

Phase C beginnt damit bei `3/127`.

## Global Constraints

- **Nur die drei Renames.** `DrylAiIndicator`, `DrylAiScope`, `DrylAiStream`,
  `DrylAiGenerate`, `DrylAiBuild` werden nicht angefasst. Sie sind unter dem
  `AiState.None`-Test keine Opt-ins; ihre Spec bekommen sie in Phase C mit ihrer
  Kategorie.
- **Kein Bruch.** `Ai` kommt hinzu, `State` bleibt als `[Obsolete]`-Alias. Entfernung
  erst im nächsten geplanten `3.0.0` (`REL-01`).
- **Kein neuer Token, keine neue Animation, kein neuer `AiState`.** `I1` hat unter
  `IDEA-05` nichts davon ausgelöst; ein Task, der das doch braucht, ist falsch geplant
  und wird gestoppt, nicht improvisiert.
- **Specs auf Englisch** (`SPEC-08`), auch wenn dieser Plan deutsch ist.
- **Ein Commit pro Task.** `DRYL.Website` ist ein eigenes Repository und bekommt seinen
  eigenen Commit (Task 7).

## Die offene technische Annahme

`I1` verspricht im `## Impact`: „Consumers get a compiler warning naming the
replacement instead of a break." Das setzt voraus, dass ein `[Obsolete]`-Attribut auf
einem Komponentenparameter an der **Razor-Call-Site** tatsächlich `CS0618` auslöst. Der
Razor-Compiler übergibt Komponentenparameter über `AddComponentParameter(seq, "State",
value)` — als Zeichenkette, nicht als Property-Zugriff. Ob daraus eine Warnung folgt,
ist eine Eigenschaft der Toolchain und **nicht** etwas, das dieser Plan annehmen darf.
Task 1 misst es, bevor Task 4 sich darauf verlässt.

Fällt die Messung negativ aus, ist der Alias immer noch korrekt (der Code compiliert
und verhält sich richtig), aber er trägt keinen Migrationshinweis. Dann gilt: Alias
bleibt wie geplant, der XML-Doc-Kommentar trägt die Migration im IntelliSense, und der
Befund wird in `I1` unter `## Decisions` nachgetragen — nicht stillschweigend
weggelassen.

**Gemessen 2026-08-11 (Task 1, erledigt): die Annahme hält.** `[Obsolete]` auf
`DrylToolCall.State` erzeugte `CS0618` an jeder Razor-Call-Site — fünf in der Komponente
selbst, eine in `DrylAgentToolCalls`, zehn in `DRYL.Website`, jede mit dem Text des
Attributs. Eine Einschränkung, die im `Obsolete`-Text berücksichtigt werden muss: die
Warnung nennt als Pfad die **generierte** Datei
(`obj/…/Components/Examples/ToolCall/States_razor.g.cs`), nicht die `.razor`-Zeile. Der
Nutzer findet die Stelle also über den Dateinamen, nicht über die Zeilennummer — der
Text muss darum den neuen Parameternamen selbst nennen, was die geplante Formulierung
tut.

## Task 2 — `AI-03` auf den Opt-in-Parameter verengen

**Files:** `harness/ai.md`

Regeltitel und Text werden auf das verengt, was die Regel meint. Der Kern ist der
Test aus `I1`:

> Rendert die Komponente mit `AiState.None` noch etwas Sinnvolles? Ja → der Parameter
> ist ein Opt-in, heißt `Ai` und hat den Default `AiState.None`. Nein → der Wert ist
> Inhalt oder Steuergröße der Komponente, trägt seinen eigenen beschreibenden Namen,
> und sein Default ist die Entscheidung dieser Komponente.

Der bisherige Absatz „Whether AI-native components … is **open and unresolved**"
entfällt — er ist beantwortet. An seine Stelle tritt die namentliche Liste der fünf
legitimen Nicht-Opt-ins mit je einem Satz Grund (`DrylAiScope`: `null` heißt „folge
`IDrylAiActivityService`", `None` heißt „AI aktiv aus" — zwei verschiedene Dinge;
`DrylAiStream`/`DrylAiGenerate`/`DrylAiBuild`: `SettleTo` ist der Zustand **nach** dem
`Generated`-Reveal, kein Schalter; `DrylAiIndicator`: der angezeigte Wert, mit `None`
rendert die Komponente nichts).

`Enforced` wird von `grep` auf **`grep` + `review`**: „ist ein Opt-in" ist nicht
greppbar. Der `Check:` benennt darum, wie `CODE-01` es vormacht, die legitimen
Nicht-Opt-ins namentlich — eine benannte Liste ist prüfbar, eine Kategorie nicht — und
verlangt vom Reviewer, dass jeder **neue** `AiState`-Parameter gegen den `None`-Test
gelesen wird.

Die Trefferzahl im `Check:` wird nicht geschätzt, sondern nach Task 6 aus dem
tatsächlichen `grep` nachgezogen (siehe Task 8).

**Verify:** `node scripts/check-harness-links.mjs` grün;
`rg -n 'open and unresolved' harness/ai.md` liefert keinen Treffer mehr.

## Task 4 — `F1 DrylToolCall`: Spec und Rename

**Files:** `specs/E3 AI/F1 DrylToolCall.md`,
`code/DRYL.Components/Components/AI/DrylToolCall.razor`,
`code/DRYL.Components/DRYL.Components.csproj`, `CHANGELOG.md`

**Spec** nach dem Format aus `SPEC-03`: `Meta` (`State: Implemented`, `Source` =
`DrylToolCall.razor` und `DrylToolCall.razor.css`), `User Story` aus Sicht des
konsumierenden Blazor-Entwicklers, `Description`, `Public API`, `Acceptance Criteria`.
Die sechs Querschnittspunkte aus `SPEC-05` werden im Spec-Text belegt: beide
Farbmodi, Enter/Exit-Animation, Tastatur und a11y (`aria-expanded`, `aria-controls`
auf dem Kopf-Button), die AI-Mode-Entscheidung explizit, die Demo-Seite in
`DRYL.Website` und der `ComponentCatalog`-Eintrag. Kriterien atomar nach `SPEC-06`,
Token statt Werten nach `SPEC-07`.

**Code:**

```csharp
[Parameter] public AiState Ai { get; set; } = AiState.None;

[Obsolete("Renamed to Ai (AI-03). The State alias is removed in 3.0.0.")]
[Parameter] public AiState State { get => Ai; set => Ai = value; }
```

Delegierendes Property, kein zweites Feld: derselbe Typ, damit weder `@bind-State`
noch die Typinferenz an einer Call-Site bricht. Beide Parameter gleichzeitig zu setzen
ist nicht unterstützt und wird im XML-Doc so gesagt — dann entschiede die
Markup-Reihenfolge, und das ist keine Zusage, die eine Bibliothek geben sollte.

Alle internen Verwendungen von `State` in der Komponente (`StatusLabel`,
`OnParametersSet`, `_prevState`, die `DrylAiIndicator`-Bindung) lesen ab jetzt `Ai`;
der Alias wird bibliotheksintern nirgends mehr gelesen. Der Kopfkommentar der Datei
zeigt `Ai="AiState.Thinking"`.

**Version und Changelog:** Dies ist der erste Task, der Bibliothekscode anfasst.
`<Version>` von `DRYL.Components` geht `2.21.0` → `2.22.0` (neuer Parameter = MINOR,
`REL-01`), und `CHANGELOG.md` bekommt unter `[Unreleased]` einen `### Added`- und einen
`### Deprecated`-Eintrag, die Task 5 und 6 fortschreiben. Kein zweiter Bump in den
Folge-Tasks — `2.22.0` trägt alle drei Renames.

**Verify:** `dotnet build DRYL.slnx -c Release` und `dotnet test DRYL.slnx -c Release`
grün; `node scripts/check-spec-coverage.mjs` meldet `1/127`;
`rg -n 'State' code/DRYL.Components/Components/AI/DrylToolCall.razor` zeigt `State` nur
noch im Alias und seinem Doc-Kommentar.

## Task 6 — `F3 DrylCanvas`: Spec und Rename

**Files:** `specs/E3 AI/F3 DrylCanvas/_Component.md` plus `S{n}`-Dateien,
`code/DRYL.Components/Components/AI/DrylCanvas.razor`,
`code/DRYL.Components/Components/AI/DrylCanvasWorkspace.razor`,
`code/DRYL.Components.Agents/Canvas/DrylAiCanvas.razor`, `CHANGELOG.md`

`SPEC-02` nennt `DrylCanvas` ausdrücklich als einen der drei Split-Kandidaten der
Bibliothek — knapp 30 Parameter, JS-Interop, Selektion, Datenbindung, Aktionen. Die
Spec wird darum als Ordner angelegt: `_Component.md` mit `Meta` (`State`, `Source` =
`DrylCanvas.razor` und `DrylCanvas.razor.css`), `Description` und `Public API`; die
Akzeptanzkriterien verteilen sich auf die `S{n}`-Dateien, jede mit `State` und ohne
`Source` (`SPEC-03`).

Schnitt der Aspekte — nach den Verantwortlichkeiten, die die Komponente ohnehin trennt:

| Datei | Inhalt |
|---|---|
| `S1 Rendering.md` | Spec-Baum, Knotentypen, leerer Zustand, Fehler, Purge |
| `S2 AI states.md` | `Ai`, Build-Line, „waiting…"-Skelette, Aura-Lebenszyklus — der Aspekt, den `I1` verändert |
| `S3 Data binding.md` | `CanvasPulseTracker`, Datenquellen, Refresh |
| `S4 Interaction.md` | `Selection`, Toolbar, Pin/Duplicate/Remove/Reorder, `OnEdit` |
| `S5 Layout and expand.md` | `AllowExpand`, Overlay, `OnWidthChanged`, Resize-Observer |

Sollte sich beim Schreiben zeigen, dass ein Aspekt nicht trägt, wird der Schnitt
angepasst und die Änderung hier vermerkt — nicht ein leerer Abschnitt gefüllt, damit
die Tabelle stimmt.

Der Rename selbst ist derselbe wie in Task 4. Die beiden bibliotheksinternen
Call-Sites — `DrylCanvasWorkspace` (gleiches Paket) und `DrylAiCanvas` (Agents) —
gehen auf `Ai`. `DrylAiCanvas` setzt in derselben Datei `State` auch auf
`DrylAiIndicator`; **das bleibt unverändert**, denn `DrylAiIndicator` ist unter dem
`None`-Test kein Opt-in und wird nicht umbenannt. Diese Unterscheidung ist die
eigentliche Falle dieses Tasks: `State=` ist nicht überall dasselbe.

`DrylCanvasWorkspace` und `DrylAiCanvas` bekommen hier **keine** Spec — sie werden nur
an einer Call-Site angefasst, was nach `SPEC-04` eine Code-only-Änderung ist. Ihre
Specs gehören zu ihrer Kategorie in Phase C.

**Verify:** `dotnet build DRYL.slnx -c Release` und `dotnet test DRYL.slnx -c Release`

## Was dieser Plan ausdrücklich nicht tut

- **Die fünf Nicht-Opt-ins nicht anfassen.** Weder Code noch Spec. `AI-03` erklärt sie,

- **`State` nicht entfernen.** Das ist `3.0.0` und braucht eine eigene Entscheidung.
- **Die restlichen fünf Specs von `E3` nicht schreiben.** Das ist Phase C.
- **`DrylCanvasWorkspace` und `DrylAiCanvas` nicht spezifizieren.** Sie werden nur an
  einer Call-Site angefasst.
- **Keinen Token, keine Animation, keinen `AiState` anlegen.**
